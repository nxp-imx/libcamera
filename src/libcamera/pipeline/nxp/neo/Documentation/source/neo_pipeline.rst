Neo ISP Pipeline Handler
========================

Neo ISP Overview
----------------

The Neo ISP is an Image Signal Processor integrated into selected NXP i.MX9
SoCs. It provides multiple programmable hardware blocks that process raw
camera images through a dedicated hardware pipeline. The pipeline input can
be either a single-exposure or a dual-exposure raw image, and the output is an
RGB or YUV image produced after processing.

User space configures the ISP pipeline to implement the control algorithms
required for image processing, including, but not limited to:

- Automatic Exposure Control (AEC)
- Automatic White Balance (AWB)
- Automatic Focus Control (AFC)
- Various image enhancement algorithms

The ISP hardware blocks are programmed from user space by supplying a set of
configuration parameters for each frame to be processed. During frame
processing, the ISP hardware also generates image statistics, which are
returned to user space and can be used to update control algorithms for
subsequent frames.

Current Neo ISP variants provide two possible output paths:

1. The main RGB or YUV processed image (frame output).
2. Optionally, when used with an RGB-IR sensor producing a 4×4 Bayer Color
   Filter Array (CFA) pattern, a secondary output that delivers a grayscale
   image derived from the infrared pixels.

The Neo ISP supports both inline and memory-to-memory operating modes. Inline
mode support is currently not implemented. In memory-to-memory mode, the ISP
can process multiple camera streams concurrently by performing camera-based
context switching.

The ISP hardware processing pipeline does not support image rescaling.


Pipeline Handler
----------------

Media Controller device graph
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The ISP is exposed by its Linux kernel driver as a media graph of V4L2 devices
and subdevices.


.. graphviz:: media/neo_isp_graph.dot


The neoisp subdevice in the ISP media graph is connected to several video
nodes. These nodes are divided into output devices, which accept data from
user space into the ISP, and capture devices, which deliver processed data
from the ISP to user space.

Output video devices (user-space to ISP)


- ``neoisp-input0``
  Receives the primary raw image buffers from the camera sensor for
  processing by the ISP.

- ``neoisp-input1``
  Available only in dual-exposure configurations. This device receives
  secondary raw buffers corresponding to the short-exposure image.

- ``neoisp-params``
  A metadata video device that queues per-frame ISP configuration
  parameters controlling the hardware processing blocks.

Capture video devices (ISP to user-space)


- ``neoisp-frame``
  Provides the RGB or YUV image produced by the ISP processing pipeline.

- ``neoisp-ir``
  Available only with RGB-IR sensors. Provides a grayscale image generated
  from the sensor’s infrared pixels.

- ``neoisp-stats``
  A metadata video device that reports image statistics generated by the
  ISP hardware during frame processing.

Front-Ends
^^^^^^^^^^

The Neo ISP pipeline handler implements a memory-to-memory operation mode.
In this configuration, the sensor device is connected to a set of downstream
V4L2 subdevices that write the raw image buffers into memory. The pipeline
handler is then responsible for passing these raw buffers, together with
their associated processing parameters, to the ISP media graph for processing.

The graph of V4L2 devices, ranging from the sensor device down to the final
video node that exposes the raw buffers in memory, is referred to as the
front-end.

In principle, the Neo ISP may be integrated into different SoCs with various
front-end device implementations, each with its own characteristics.
To account for these variations, the Neo ISP pipeline handler relies on
front-end handler implementations to abstract the details of the specific
front-end devices.

Currently, the pipeline handler provides front-end handler implementations
for the following media devices:

- `ISI`
- `VIVID`

ISI front-end
~~~~~~~~~~~~~

On i.MX9 SoCs in which the Neo ISP is instantiated, MIPI-CSI2 camera streams
are written to memory through an Image Sensor Interface (ISI) device.
At the media-graph level, the ISI device consists of:

1. A ``crossbar`` subdevice with multiple sink pads representing video stream
   hardware initiators. Each MIPI-CSI2 port instance is connected to one sink
   pad.

2. A set of processing pipes capable of scaling, performing color space
   conversion, and writing video streams to memory through DMA. Each pipe
   consists of a ``mxc_isi.N`` subdevice and an associated video node
   ``mxc_isi.N_capture``.

   When raw cameras are used, the video stream output by the sensor is in
   Bayer format, which cannot be rescaled or have its pixel format modified
   by the ISI. In this case, the pipe operates in bypass mode, and the incoming
   video stream is written unmodified to memory.

.. graphviz:: media/front_end_isi_graph.dot

The above example shows a media graph in which the ISI device consists of one
crossbar and eight channel pipes. Two independent MIPI-CSI2 ports are
connected to the crossbar sink pads.

The first MIPI-CSI2 port is shared by four ``mx95mbcam`` cameras. Their video
streams are multiplexed over different Virtual Channels of the same CSI port
using GMSL serializers and a deserializer. Each camera stream is routed to a
dedicated ISI pipe and, consequently, to a dedicated video node.

The second MIPI-CSI2 port is connected to a single ``ar0144`` camera. Its video
stream is similarly routed to an individual ISI pipe and video node.

Cameras multiplexed over the same MIPI-CSI2 port share media pads belonging to
multiple media entities, including the GMSL deserializer, the MIPI-CSI2 block,
the Pixel Formatter, and the ISI crossbar. Individual video stream formats are
multiplexed on these shared pads using V4L2 streams and routing configurations.

Underlying devices may impose limitations on the supported transitions between
different video streams on a shared pad. For example, the current ISI driver
implementation does not allow reconfiguring the format of a V4L2 stream on a
crossbar sink pad while another V4L2 stream remains active on the same pad.

Such limitations introduce constraints on the configurability (formats,
orientation, and related parameters) of cameras that share portions of the
media graph. These device-specific constraints are handled by the ISI
front-end implementation.


VIVID front-end
~~~~~~~~~~~~~~~
The VIVID front-end can be used for development and testing purposes. It
allows feeding the Neo ISP with raw buffers generated by a Test Pattern
Generator or produced offline.

See the :doc:`front_end_vivid` documentation for more details.


Pipeline Handler
^^^^^^^^^^^^^^^^

Camera Streams
~~~~~~~~~~~~~~

The pipeline handler expects the V4L2 camera driver to expose one or more
streams.

* ``image0`` is mandatory. For standard single dynamic range (SDR) camera
  operation, it corresponds to the single image exposure produced by the
  sensor.

* ``image1`` (auxiliary image) is optional. It is present on cameras that
  expose two distinct image captures, typically transmitted over different
  MIPI-CSI Virtual Channels. This is currently supported for the following
  use cases:

  * **HDR sensors**: ``image0`` contains the long-exposure image, while
    ``image1`` contains the short-exposure image.

  * **RGB-IR dual-context sensors**: the sensor outputs multiple variants of
    the captured image using independently managed exposure register
    contexts. ``image0`` typically carries the RGB-optimized exposure, and
    ``image1`` the IR-optimized exposure.

* The ``embedded data`` stream is optional. Some cameras expose per-frame
  embedded data associated with an image through a separate metadata stream.
  This stream can be made available to the IPA for use by image processing
  and control algorithms.

The camera streams described above map to V4L2 streams exposed on the
camera subdevice source pad.


Pipeline Modes
~~~~~~~~~~~~~~

Internally, the pipeline handler selects an operating mode based on its
configuration. Each mode defines a specific mapping between the camera
streams and the ISP video nodes handled by the pipeline handler.

.. list-table::
   :widths: 15 15 20 25
   :header-rows: 1

   * - Mode
     - Camera streams
     - ISP video nodes
     - Description
   * - Standard
     - ``image0``
     - ``neoisp-input0``, ``neoisp-frame``
     - Standard single-exposure capture mode
   * - HDR merge
     - ``image0``, ``image1``
     - ``neoisp-input0``, ``neoisp-input1``, ``neoisp-frame``
     - High Dynamic Range (HDR) captures merged by the ISP
   * - RGB-IR
     - ``image0``
     - ``neoisp-input0``, ``neoisp-frame``, ``neoisp-ir``
     - RGB-IR sensor, single-capture operation
   * - RGB-IR dual-capture
     - ``image0``, ``image1``
     - ``neoisp-input0``, ``neoisp-frame``, ``neoisp-ir``
     - RGB-IR sensor, dual-capture operation

.. note::
   In RGB-IR mode, a single raw sensor capture is processed once by the ISP to
   produce two outputs: an RGB or YUV image derived from the RGB pixels of the
   raw image, and a grayscale image derived from the IR pixels.

   In contrast, RGB-IR dual-capture mode requires the ISP to process two
   separate RGB-IR raw captures: one with exposure optimized for the RGB
   pixels, and another with exposure optimized for the IR pixels.
